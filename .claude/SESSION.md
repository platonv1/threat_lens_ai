### `backend/Dockerfile` migrations gap — fixed (this session)

Root cause: the Dockerfile only `COPY`'d `app/`, not `alembic.ini`/`migrations/`, and nothing ran `alembic upgrade head` on container start — so a freshly built container had no tables until someone manually `docker compose cp`'d the migration files in and ran alembic by hand (hit twice now, in the URL Scanner frontend session and the Message Scanner session).

Fix: added `backend/docker-entrypoint.sh` (`alembic upgrade head` then `exec "$@"`), set it as the image's `ENTRYPOINT`, and `COPY`'d `alembic.ini`/`migrations/` into the image alongside `app/`. Using `ENTRYPOINT` rather than editing `CMD` matters here — `docker-compose.yml`'s `backend.command` overrides `CMD` (to add `--reload`), which would have silently dropped a migration step added there; `ENTRYPOINT` always runs first regardless of how `CMD` is overridden.

Verified: `docker compose down -v` (wipes the `postgres_data` volume) → `docker compose build backend` → `docker compose up -d db backend` against the now-empty DB, with **no manual migration step** — logs show `alembic.runtime.migration ... Running upgrade  -> bd7a0f83bdb0` on startup, `GET /health` → `200`, and `POST /scan/email` persists successfully on the first request. Also verified idempotency: `docker compose restart backend` against the now-migrated DB re-runs alembic as a fast no-op with no errors. Backend test suite unaffected (43/43 still passing — no application code changed).

A screenshot is OCR'd to text, shown in the same textarea for the user to review/edit, then flows through the unchanged `/scan/email`/`/scan/sms` pipeline.

Backend:
- `backend/app/services/ocr_service.py`: `extract_text(image_bytes: bytes) -> str`, wrapping an EasyOCR `Reader`. The `Reader` is a lazily-initialized module-level singleton (built on first call, not at import time) — importing the module doesn't pay EasyOCR's model-load cost unless OCR is actually used, and repeated calls reuse the same loaded model.
- `backend/app/api/routes/ocr.py` (new router, not added to `scan.py` — no persistence, no risk scoring): `POST /ocr/extract`, multipart field `image`. Validates content-type (`image/jpeg`, `image/png`, `image/webp`) and size (≤8MB) before calling `extract_text` in a threadpool (matches the existing WHOIS/DNS/SSL pattern in `scan.py`, since OCR inference is CPU-bound). Returns `200 {"text": ...}` (empty string if no text found — not an error) or `422` for invalid uploads. The image is never written to disk or the database.
- This resolves the previously-open "OCR engine choice" item in favor of EasyOCR.

Frontend:
- `frontend/src/lib/api.ts`: `extractText(image: File)` — posts `multipart/form-data` (the only function in this file that isn't JSON), throws `ScanError` on non-2xx via the existing `extractErrorMessage` path.
- `frontend/src/components/MessageScanForm.tsx`: gained a "Paste text"/"Upload image" mode toggle. Client-side rejects oversized/wrong-type files before any network call; on a successful extraction, pre-fills the existing `text` state and switches back to paste mode (editable); a blank/whitespace-only result shows an inline "no text detected" message instead of silently leaving the box empty. ### `scans.scan_type` formalized as a real enum (this session)

Was a free-text `String(20)` column with no DB-level validation, despite only ever holding five real values (`url`, `email`, `sms`, `image`, `qr`) in practice.

- `backend/app/models/scan.py`: added `ScanType(str, enum.Enum)` and mapped `Scan.scan_type` to a SQLAlchemy `Enum(ScanType, name="scan_type_enum", values_callable=..., validate_strings=True)`. `values_callable` makes SQLAlchemy store the enum's lowercase `.value` (`"url"`) rather than its default of the member `.name` (`"URL"`), so existing rows/API contracts are unaffected. `validate_strings=True` means invalid values raise a Python-level `StatementError` on flush even on backends (like the SQLite test DB) that don't get a native DB-level CHECK — confirmed via `test_scan_type_rejects_invalid_value`.
- `backend/app/schemas/scan.py`: `ScanResponse.scan_type` changed from `str` to `ScanType` — since it's a `str` subclass, JSON responses are unaffected (`"scan_type": "url"`, not `"ScanType.URL"`), but the OpenAPI schema now documents the closed set of allowed values (verified via `/openapi.json`).
- All service call sites (`url_scan_service`, `message_scan_service`, `image_scan_service`, `qr_scan_service`, `scan_persistence`, `ollama_service`, the `/scan/*` routes) updated to pass `ScanType.X` members instead of raw string literals, for compile-time typo protection.

### Phase 7: Report Export (this session, across two sub-sessions)

Implemented the plan in `.superpowers/sdd/2026-08-05-scan-report-export/` (5 tasks: backend service, route, frontend client function, frontend button, docs + verification).

Backend:
- `backend/app/services/report_service.py`: `generate_report(scan: Scan) -> bytes`, building a PDF in-memory with `reportlab` (`SimpleDocTemplate`/`Table`/`Paragraph` flowables) — title, type/created-at, verdict + risk score, input text, a findings table (check/severity/message, empty-state "No issues found." when there are none), and the AI summary. All scan-derived text is `xml.sax.saxutils.escape()`'d before going into a `Paragraph`, since reportlab parses embedded XML-ish markup. For each of the scan's `uploaded_files` (currently only ever populated by Screenshot Scanner scans — QR scans decode-and-discard their image), the original image is embedded via `reportlab.platypus.Image` if the on-disk file still exists, else a "Image unavailable." fallback line — so a manually-deleted upload file degrades gracefully instead of crashing report generation.
- `backend/app/api/routes/scan.py`: `GET /scan/{scan_id}/report` — 404 via the existing `Scan` lookup pattern if the id doesn't exist, otherwise returns a `Response(content=pdf_bytes, media_type="application/pdf", headers={"Content-Disposition": ...})` with `filename="scan-{id}-report.pdf"`. Never persisted to disk or the DB — generated fresh on every request.
- `reportlab` added to `backend/requirements.txt`.

Frontend:
- `frontend/src/lib/api.ts`: `downloadReport(id)` — fetches the endpoint, reads the blob, and triggers a browser download via a temporary anchor element (this project's first binary/file-download client call; everything before was JSON).
- `frontend/src/components/ScanResultView.tsx`: a "Download Report" button, shared by both the Results view (right after scanning) and the History detail view since both render this one component.
